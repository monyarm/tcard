# tcard web UI

Status: implemented 2026-11-19 (`tcard/web/`). Date: 2026-11-19.

A local web page over the same data the CLI uses: pick a system, filter, read the
32-column card, press print, and the server runs the CLI and pipes it into `tp`.

The CLI stays the only renderer. The web layer adds no card logic, so a card in
the browser is byte-identical to `tcard … | tp`.

## Shape

- New package `tcard/web/` — `server.py`, `static/index.html`, `static/app.js`,
  `static/style.css`. Standard library only (`http.server`,
  `ThreadingHTTPServer`, `json`, `subprocess`, `webbrowser`), no build step, no
  npm, no template engine. This matches the repo's dependency-free rule
  (`dependencies = []`, tests run without pytest).
- Entry points: early `web` dispatch in `cli.main` (`tcard web --port 8765`),
  plus a `tcard-web` console script in `pyproject.toml`.
- Binds `127.0.0.1` by default (a printing endpoint must not be on the LAN).
  `--host` exists but stays opt-in. `--dry-run` renders and returns text without
  invoking `tp`, so the UI and tests can be exercised without paper.

## Data flow

Two paths, deliberately different:

| path | mechanism |
| --- | --- |
| browsing (systems, kinds, record list, facets) | imports `tcard.sources.registry` in-process and calls `Kind.records()` |
| preview and print | subprocess `python3 -m tcard <system> <kind> <name> [--source] [--cols] [--brief]`, then pipe stdout into `tp` |

Browsing must be in-process: it needs `records()` for every kind, and shelling
out per request would re-load multi-thousand-row indexes. Printing must be a
subprocess: `tp` renders the CLI's exact stdout, and the CLI owns matching,
`--source` choice and layout. Preview uses the same subprocess path (cached per
argument tuple) so what is on screen is what prints.

`tcard` is not installed on PATH on this machine (`which tcard` → nothing), so
the server spawns `[sys.executable, "-m", "tcard", …]` with `cwd` at the repo
root.

### Query form

The list sends the record's `name` as one argv element. Bare names resolve for
every kind (`merit beautiful` searches all groups, `auspex:scry_the_soul` is
optional). `display()` is *not* a query: it appends parentheticals the matcher
does not expect (`Beautiful (Look)`).

When the same name exists in several books, the row carries its source and the
request passes `--source`; the CLI's `prefer` order otherwise decides, and the
facet chip shows which book was used.

## Index and facets

Measured load times with warm caches (full sweep of all 6 systems, 108 kinds):

| system | biggest kind | time |
| --- | --- | --- |
| dnd:5e | monster 4 683 | 0.2 s |
| pf:1e | monster 6 937 | 0.1 s |
| pf:2e | monster 7 912 | 2.3 s |
| vtm:v5 | discipline 405 | 0.1 s |
| vtm:v20 | discipline 944 | 0.1 s |
| cp:2020 | cyberware 983 | 0.0 s |

So: load lazily per `(system, kind)` on first request, keep in memory for the
process lifetime, and offer a refresh button. First use of a pf:2e kind may
trigger its sparse checkout, so the UI shows a spinner naming the kind.

Facets are declared per system and computed from the index records (no card
build, no network):

- `dnd:5e` — source, level, school, category, type, rarity, className
- `pf:1e` — section (derived from the index URL path, e.g. `magic-items/artifacts`);
  the index rows only hold `{name, url}`
- `pf:2e` — pack (derived from the index `path`, e.g. `spells`, `bestiary-1`);
  rows only hold `{name, path}`
- `vtm:v5` — discipline, group, dots, level
- `vtm:v20` — tradition, level, group
- `cp:2020` — type, category, subcategory, class, surgery, book

A generic fallback keeps this honest: any other scalar key with 2–40 distinct
values becomes a facet automatically. Keys with more than 40 values (`cost`,
`hc`, `wa`) stay out of the facet list and remain searchable by name only.

Filtering is server-side: `q` is a case-insensitive substring over the record
name, facets are exact matches (multi-select = OR within a facet, AND across
facets), results are capped at 100 with a "load more" offset. Facet counts are
computed over the unfiltered index so they do not collapse as filters are added.

## Endpoints

All JSON, `GET` except print:

- `GET /api/systems` → `{systems: [{id, kinds: [...]}]}`
- `GET /api/index?system=&kind=&q=&<facet>=v1,v2&offset=` →
  `{count, total, facets: {key: [{value, count}]}, rows: [{name, label, source, facets}]}`
- `GET /api/card?system=&kind=&name=&source=&cols=&brief=` → `{text, lines, error}`
  (subprocess, no printing, cached)
- `POST /api/print` same parameters → runs the CLI, pipes stdout to `tp`, returns
  `{ok, text, error, tp_code}`
- `GET /api/health` → `{tp: <path or null>, tcard: true}`

Errors keep the CLI's contract: unknown system/kind → 404, `cols` outside
8–200 → 400, CLI exit 1 (no match) → 404 with the CLI's stderr line, CLI
exit 3 (network/cache) → 502 with the message. `tp` failure is reported with its
exit code and stderr, and the UI shows the rendered text either way so the user
can retry.

## Printing

`print_card()` runs, in order:

```python
cmd = [sys.executable, "-m", "tcard", system, kind, name, "--cols", str(cols)]
if source: cmd += ["--source", source]
if brief: cmd += ["--brief"]
done = subprocess.run(cmd, cwd=ROOT, capture_output=True, timeout=180)
if done.returncode: return error(done.stderr)
sent = subprocess.run([tp_binary], input=done.stdout, capture_output=True, timeout=300)
```

`tp` with no file argument reads stdin as text and streams it page by page
(verified in `~/.nix/packages/tp.py`: the `args.file in (None, "-")` branch
iterates `sys.stdin.buffer`), so `tcard … | tp` and this path are equivalent.

A single lock serialises prints. Batch selection prints one CLI run and one `tp`
run per card, so each card gets its own feed; the UI shows progress per row.
`tp` is located on PATH at startup and reported in `/api/health`; a missing
binary disables the button with the reason instead of failing after the click.

## Sharing

`--serve` puts a proxy in front of the loopback server and turns on an access
key; the server itself never binds a network interface.

- `--serve tailscale` (also `--serve`, `auto`): `tailscale serve --bg <port>`,
  then the URL comes from `tailscale status --json` (`Self.DNSName`). Tailnet
  devices only.
- `--serve funnel`: the same through `tailscale funnel --bg`, which publishes on
  the internet. Funnel has to be allowed in the tailnet ACL.
- `--serve cloudflare`: `cloudflared tunnel --url http://127.0.0.1:<port>`, with
  the public `trycloudflare.com` URL parsed out of its output. A new URL each
  start. `--serve cloudflare:NAME` runs a named tunnel instead.
- `--serve auto` picks tailscale when its binary exists, else cloudflare.

`tailscale serve` writes serve config through the local API, which needs root or
the user as operator; on failure the message includes
`sudo tailscale set --operator=$USER`. SIGTERM is turned into a clean shutdown so
the cloudflared child is terminated rather than orphaned.

Auth: the process generates a key (`--key` overrides) and prints
`https://host/?k=<key>`. That first request sets an HttpOnly `tcard_key` cookie
and redirects to the same path without the key. Every route, including the
static files, is behind the cookie in shared mode, so a bare hostname shows only
a key prompt. `--view-only` makes `POST /api/print` return 403 while browsing
still works.

## UI

Three columns, no framework:

- **Systems rail** — the six systems with their kind counts.
- **Filter column** — kinds for the current system, name search box, facet
  dropdowns (each value with its count), and a clear-filters button.
- **Results and preview** — rows of `name · facet chips · source`, a checkbox for
  batch print, the selected card rendered in a 32-column monospace block (with a
  line count and a "fits N lines of paper" hint), and the print button.

Top bar: `cols` selector (8–200, default from config), `brief` toggle, refresh
index, printer status dot. URL hash keeps `system/kind/q/facets` so reload and
bookmarks work. Keyboard: `/` focuses search, `Enter` previews the first hit,
`p` prints it.

Everything the page shows is printable, but nothing prints without a click, and
the print button is disabled while a job is running.

## Tests

`tests/test_web.py`, wired into the existing runner (module-level `test_*`
functions, no pytest, no network):

- facet derivation from a stub registry (declared keys, auto-detected keys,
  high-cardinality exclusion)
- filtering, pagination and facet counts on a fixed record set
- CLI argv construction for name, source, cols, brief
- preview caching (same args → one subprocess)
- print path with `subprocess.run` monkeypatched: asserts `tp` receives the CLI's
  stdout bytes on stdin, and that a CLI failure stops before `tp` from being
  called
- error mapping: unknown kind 404, bad cols 400, CLI exit 1 → 404, exit 3 → 502

Handler functions take a parsed query dict, so tests call them directly without
opening a socket.

## Build order

1. `tcard/web/data.py` — index cache, facet derivation, filtering, query string
   per record. Tests first.
2. `tcard/web/print.py` — CLI runner, `tp` pipe, error mapping, lock, dry-run.
3. `tcard/web/server.py` — routing, JSON encoding, static file serving; tests
   against the route table.
4. `static/` — HTML, CSS, JS.
5. `cli.main` `web` dispatch + `pyproject.toml` script + README section + this
   spec updated with what actually shipped.
6. Live check: `curl` each endpoint, `--dry-run` a print, then one real print
   against the printer.

## What the build added beyond the plan

- Facet codes are shown as the words the cards print (`V` → Evocation, `P` →
  Pistol, `N` → None for surgery) through a small label table in
  `web/data.py`; the filter value stays the raw code so it matches the records.
- Rows carry a pre-joined `chips` string (book plus up to three labelled facet
  values) rather than making the browser repeat the mapping.
- The page listens for `hashchange`, so pasted links and back/forward reload the
  list instead of leaving stale rows.
- `status`/`print` responses echo the CLI's stderr line, and the print button
  reports a missing `tp` from `/api/health` before the click rather than after.

## Non-goals

- PNG cards (the backend is still blocked on the `tp` stdin image patch).
- Editing or adding records; the UI is read-only over the adapters.
- Auth, multi-user, or LAN exposure by default.
- A server-side cache of rendered cards beyond the process lifetime; the
  adapters already cache their own fetches on disk.
